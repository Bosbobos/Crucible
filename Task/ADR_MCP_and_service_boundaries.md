# ADR-002. Границы сервисов и MCP-интерфейс внешнего агента

Дата: 13 ноября 2026 года. Статус: предлагаемое изменение ТЗ, не описание реализованной системы.

Применять вместе с `TZ_Crucible.md`. В части агентского интерфейса, ответственности worker и зависимых критериев приёмки этот документ заменяет противоречащие положения версии 1.0. Учебная программа и `curriculum_manifest.json` не меняются. Исходное ТЗ этим файлом физически не переписано.

## 1. Решение

Основной интерфейс внешнего агента к работающему приложению — предметный MCP-сервер `study-mcp`. Он предоставляет контекст и проверяемые действия, обращаясь к `study-api`. Файлы остаются основным способом авторинга учебных материалов и резервным форматом экспорта пользовательской истории. Двусторонний файловый обмен через постоянно опрашиваемый inbox больше не является обязательным основным каналом.

Агент и модель работают во внешнем host-приложении. Наше приложение не вызывает LLM, не запускает автономного агента и не содержит встроенного чата. MCP-сервер не содержит модель и не заменяет доменный backend.

Сохраняется один основной модульный backend. Не выделять отдельные сервисы каталога, прогресса, таймера, рекомендаций и авторизации ради количества контейнеров. MCP-адаптер — интеграционная граница, а не новый самостоятельный бизнес-домен.

## 2. Компоненты и ответственность

| Компонент | Ответственность | Запреты |
|---|---|---|
| `web` | Интерфейс и reverse proxy | Нет прямого доступа к БД, Redis, RabbitMQ |
| `study-api` | Учебные материалы по опубликованной ревизии; попытки, вопросы, комментарии, прогресс, планы; валидация команд; права и аудит | Не вызывает LLM; не ждёт worker для сохранения результата или комментария |
| `review-worker` | Фоновые отчёты, экспорты, проверяемые производные артефакты; отдельная очередь и учёт выполнения | Не является транспортом интерактивного диалога; не пишет напрямую в доменные таблицы API; не генерирует математический разбор через LLM |
| `study-mcp` | MCP tools/resources/prompts; перевод предметных вызовов в ограниченный API; структурированные ответы | Нет собственной БД прогресса; нет прямого SQL, доступа к Redis/RabbitMQ или операторских полномочий |

Название `review-worker` можно сохранить для совместимости; переименование в `jobs-worker` не обязательно. Если оно выполняется, обновить Compose, документацию, тесты и правила firewall согласованно.

Внутри API выделить модули `content`, `attempts`, `planning`, `progress`, `reviews`, `agent_access`. Web- и agent-endpoints используют один application/domain слой. MCP-адаптер не импортирует ORM-модели API и не копирует расчёт освоения или повторений.

Схема:

```text
браузер -> web -> study-api -> PostgreSQL / study
                       |  -> Redis
                       |  -> transactional outbox -> RabbitMQ -> review-worker
                       |                                      -> PostgreSQL / jobs
                       |                                      -> exports / reports
внешний agent host -> study-mcp -> ограниченные endpoints study-api

агент-автор -> content/ в Git -> validate -> проверка -> публикация ревизии
```

Соединения показаны логически, а не как разрешение любых сетевых потоков. Все межкомпонентные доступы отражаются в матрице firewall.

## 3. Соответствие дисциплине и пределы утверждений

В документе курса прямо перечислены отдельные front, back и сервис выполнения отдельных действий, а также БД, кэш и брокер. Исходная структура соответствует этой форме минимального сценария. Однако это не гарантия оценки и не доказательство глубокой предметной микросервисной декомпозиции.

Представлять систему как небольшой набор независимо запускаемых компонентов: основной backend, асинхронный сервис обработки и два интерфейса — пользовательский и агентский. Не утверждать, что каждый контейнер автоматически является самостоятельным бизнес-микросервисом.

Если появится отдельное требование преподавателя о двух независимых предметных backend-сервисах, оформить новое решение о границах. Не считать тонкий MCP-прокси автоматическим выполнением такого дополнительного требования.

## 4. Транспорт и запуск

### P: локальный агент

Исходное предположение — используется локальный CLI/IDE/desktop host с MCP-поддержкой. Проверить это на реально выбранном пользователем клиенте до реализации; не выдавать предположение за известный факт.

Предпочтительный начальный транспорт — `stdio`: host запускает `study-mcp` как дочерний процесс. Адаптер обращается к работающему API по авторизованному HTTP через предусмотренную точку входа. Секрет API выдаётся только для профиля владельца и разрешённых агентских действий. Логи MCP-процесса выводятся в stderr, stdout резервируется под протокол.

Отдельный постоянно работающий MCP-контейнер не обязателен. Сохраняются шесть основных контейнеров `daily` и девять `assessment` из исходного ТЗ, плюс локально запускаемый MCP-процесс. Это не «три процесса во всей системе» и не четвёртая БД.

### Опциональный HTTP-профиль

При действительной необходимости сетевого MCP-клиента использовать Streamable HTTP. Этот профиль — отдельный способ запуска того же адаптера, не вторая реализация бизнес-логики. При отдельном контейнере он добавляет один контейнер к выбранному профилю.

Локальный HTTP listener публиковать только на loopback; проверять Origin и авторизацию, не считать localhost достаточной защитой. Удалённый доступ требует TLS и проверенной схемы авторизации, совместимой с выбранным host. Для interoperable OAuth-профиля использовать требования MCP, включая проверку audience, scopes и metadata discovery. Токен, предъявленный MCP-серверу, нельзя слепо пересылать в backend как универсальный пароль: backend получает корректную отдельную identity/делегирование с ограниченными правами.

Клиент, SDK, версия MCP и транспорт фиксируются в `docs/mcp-compatibility.md`. На дату исследования официальная документация указывает редакцию 2026-07-28. Выбор версии реализации зависит от фактической поддержки host и SDK. Не писать JSON-RPC, negotiation и совместимость вручную при наличии подходящего поддерживаемого SDK. Устаревший HTTP+SSE не выбирать основой новой реализации.

## 5. Контракт контекста

`get_study_context` — основной вход. Один запрос должен возвращать компактный, согласованный контекст для продолжения обсуждения, а не выгрузку всего vault.

Обязательные данные:

- цель чтения: текущая попытка, конкретная попытка или вопрос;
- ID задачи/попытки/вопроса, опубликованная версия условия;
- текущий сохранённый пользовательский ход и подпункт;
- вопрос и связанные комментарии;
- самооценка отдельно от замечаний агента;
- использованная помощь, уже раскрытые подсказки;
- ссылки на адресные ядро, теорию и интерактив;
- `attempt_revision`, `question_revision` при наличии, `content_revision`, `generated_at`;
- действующий режим помощи, ограничения на раскрытие материалов;
- при необходимости несколько релевантных прошлых затруднений, а не вся история.

Контекст отражает последнюю подтверждённую API запись, а не несохранённый текст в браузере. UI показывает статус сохранения. Сервер получает согласованный набор связанных данных; переход к файлам неизменяемой версии контента не должен подменять старую редакцию новой.

Для больших ответов — явные лимиты, пагинация и адресное расширение. Возвращать структурированные поля и короткое читаемое представление. Не вводить векторную БД до появления измеримой необходимости: начать с метаданных, связей и обычного текстового поиска.

## 6. Предметные инструменты

Названия ниже — контракт предметной семантики; точные схемы зафиксировать и покрыть тестами.

| Инструмент | Уровень | Назначение и ограничение |
|---|---|---|
| `get_study_context` | P | Актуальный контекст без скрытых решений; не меняет результат или счётчики помощи |
| `list_review_queue` | P | Приоритетная очередь явных вопросов и затруднений; доступна без worker |
| `begin_tutoring` | P | Явно фиксирует начало математического обсуждения выбранной попытки; не вызывается для обычного чтения статистики |
| `append_review` | P | Добавляет комментарий с привязкой к исходной ревизии; не переписывает пользовательский текст |
| `propose_progress_correction` | P | Создаёт предложение об исправлении оценки с причиной; саму оценку не меняет |
| `search_materials` | D | Находит опубликованные материалы по теме/навыку/запросу с учётом доступности |
| `get_material` | D | Читает разрешённую часть условия, ядра, теории или описания интерактива по ID и ревизии |
| `reveal_help` | D | Отдельное раскрытие скрытой помощи с проверкой разрешения и регистрацией события; не маскируется под read-only |
| `get_progress_summary` | D | Детерминированные показатели с периодом, ревизией данных и основаниями |
| `propose_plan_adjustment` | D | Предложение изменения фокуса/нагрузки, применяемое владельцем |
| `request_export` | D | Ставит задачу экспорта в outbox/очередь, возвращает job_id |
| `get_job` | D | Статус задания; ссылки на результат только после готовности |

Авторский профиль может дополнительно иметь `validate_content_revision`: проверка заранее зарегистрированной кандидатной ревизии. Не принимать произвольную shell-команду или неограниченный путь. Этот инструмент не включать в обычный учебный набор.

Не создавать универсальные `execute_sql`, `run_shell`, `write_any_file`, `call_any_endpoint` и не превращать каждый REST endpoint в отдельный MCP tool. Обязательное число инструментов определяется сценариями, а не стремлением продемонстрировать все возможности MCP.

## 7. Resources и prompts

Resources — адресное чтение: например, `study://attempts/<id>/revisions/<revision>` и `study://topics/<id>/core/<content_revision>`. Наличие URI не даёт права чтения: проверяются владелец, полномочия и политика раскрытия. Один и тот же материал выдаётся через tool и resource из общего обработчика, без отдельных правил доступа.

Prompts — необязательные шаблоны сценариев: `review_attempt`, `explain_gap`, `weekly_review`. Они задают стиль разбора: сначала ход пользователя, затем локализация ошибки, минимальная помощь, адресная теория, контрольный пример и краткий сохраняемый вывод. Они не являются механизмом авторизации и не гарантируют поведение модели.

Основной сценарий должен работать через tools без обязательной поддержки resources/prompts/subscriptions конкретным host. Поддержку этих возможностей проверить и явно указать. Уведомление об изменении resource не означает автоматическую актуализацию уже загруженного контекста модели: перед значимой записью проверять ревизии.

MCP не создаёт учебный интерактив в браузере: агент может найти и сослаться на его конфигурацию/страницу, пользователь работает с визуализацией в приложении. Перенос интерактивного UI внутрь агентского host не входит в P/D.

## 8. Запись, версии и согласие

Все инструменты записи используют общий application слой API. Субъект и профиль выводятся из проверенной identity, а не из произвольного `profile_id` в аргументах.

Для изменяющих команд обязательны `command_id`, предметный ID, необходимые ожидаемые ревизии и аудит. Один command_id с тем же payload возвращает прежний результат, с другим payload — конфликт. Повтор с новым command_id считается другой командой; host обязан повторять неизвестный исход с прежним ID.

`append_review` сохраняет комментарий рядом с исходной попыткой. Если пользователь уже изменил попытку, комментарий можно сохранить как относящийся к старой ревизии с явной пометкой, не применять к актуальной версии автоматически. Предложение, изменяющее прогресс, требует проверки актуальной ревизии при подтверждении.

Изменения оценки, расписания, состояния освоения и закрытие вопроса выполняет владелец через доверенный UI. Агент создаёт предложения. Булев аргумент `confirmed=true`, присланный агентом, не является пользовательским подтверждением.

Простое чтение агентом истории не считается помощью. Математический диалог по активной попытке фиксируется отдельным действием `begin_tutoring` или кнопкой сайта. Если обсуждение затрагивает новую незавершённую попытку, это отражается именно в ней. Разбор завершённой попытки сам по себе не делает задним числом её прошлое решение несамостоятельным.

Приложение не наблюдает весь внешний чат и не доказывает отсутствие посторонней помощи. Предусмотреть ручную отметку/исправление с причиной. Ответ агента, пришедший вне протокола, нельзя автоматически учесть без интеграции host.

## 9. Синхронная и фоновая работа

Чтение текущего контекста, очередь вопросов, начало обсуждения, сохранение комментария и создание предложения не зависят от RabbitMQ или worker. API возвращает успех после своей устойчивой транзакции, а не после сохранения Markdown-копии.

Отчёты и экспорты — фоновая работа. API в одной транзакции создаёт job/request и outbox-событие; dispatcher доставляет его в RabbitMQ. Worker идемпотентно строит артефакт и сообщает готовность. При остановке broker/worker обычная подготовка и MCP-разбор продолжаются, но задания ожидают обработки. Не обещать доступность при отказе самого API/его БД.

Обычная реплика агента не должна проходить цепочку MCP -> RabbitMQ -> worker -> inbox -> API. MCP — интерфейс взаимодействия; брокер — механизм отложенного выполнения. Они решают разные задачи.

Сохраняются исходные требования outbox, publisher confirm, проверки маршрутизации, ack после устойчивого эффекта, DLQ и защиты от повторной доставки. Новое сообщение или повтор не должны дублировать комментарий.

## 10. Файлы и два режима агента

| Режим | Основной путь |
|---|---|
| Учебный разбор | MCP: контекст, материалы, комментарии, предложения |
| Авторинг задач/ядер/теории | Файлы в Git: изменения -> validation -> проверка -> публикация |
| Долговременная переносимость | Экспорт JSON/Markdown |
| Нет MCP-поддержки у host | CLI над теми же командами API или явный импорт проверяемого пакета |

Автоматический watcher `workspace/inbox` из версии 1.0 не обязателен. Если он уже реализован, его можно сохранить как дополнительный транспорт, но он обязан использовать те же проверки и ключи команд; отдельная бизнес-логика и двусторонняя синхронизация БД с произвольным Markdown запрещены.

Агент-автор не получает право считать отредактированный на диске файл сразу опубликованным. Рабочее дерево и опубликованная ревизия различаются; читатель и попытка привязаны к неизменяемой опубликованной версии.

Учебный профиль имеет только необходимые права и не видит runtime volumes, backups, секреты и закрытые пробники. Авторский/разработческий профиль обладает более широким доступом. Агент с полноценным shell и доступом к секретам может обойти MCP; это не устранить соглашением в AGENTS.md. Для реальной изоляции нужны ограничение прав ОС, mount и сетевого доступа.

Чтение официального решения сервер ограничивает, но агент может вывести решение самостоятельно. Политика помощи уменьшает случайное раскрытие и поддерживает методику, а не гарантирует отсутствие подсказок от модели.

## 11. Безопасность и сеть

Для stdio-профиля MCP-процесс обращается только к разрешённому API; отдельного входящего MCP-порта нет. Путь к API, identity и секреты заданы конфигурацией оператора, не аргументами модели.

Для сетевого профиля адаптер не включается в сегмент PostgreSQL/Redis/RabbitMQ. Его единственный предметный downstream — ограниченный API. Сохранить сегментацию и демонстрации firewall из исходного ТЗ. Запрет сетевого доступа и отказ по отсутствию scope показывать как разные механизмы, не выдавать 403 за срабатывание firewall.

Разделить права чтения учебного контекста, добавления комментария, создания предложения, раскрытия помощи и авторинга. Чтение тоже требует авторизации. MCP annotations описывают поведение инструментов, но не реализуют ограничения; enforce выполнять на сервере.

Markdown и ответы агента — недоверенные данные. Запретить выполнение встроенного кода, неконтролируемую загрузку URL, path traversal и произвольное чтение файлов. Не журналировать токены и полные личные тексты по умолчанию. Аудит содержит actor, command_id, предметные ID, ревизии, время и результат.

## 12. Уровни готовности

### P — к представлению

Существующий продуктовый срез и требования инфраструктуры курса сохраняются. Дополнительно обязательны:

1. Реально подключённый внешний MCP-host с зафиксированной конфигурацией и версиями.
2. Пять инструментов уровня P из раздела 6.
3. Сценарий: сохранённая попытка -> вопрос -> получение контекста -> комментарий -> появление в UI.
4. Сценарий предложения исправления: агент предлагает, владелец подтверждает, API пересчитывает прогресс.
5. Проверка повтора command_id, устаревшей ревизии и недопустимого действия.
6. Остановка worker не ломает контекст и запись комментария; экспорт ожидает возобновления.
7. Экспорт данных остаётся доступным, но подготовка файлового пакета не обязательна перед каждым диалогом.

При малом времени демонстрировать математический комментарий на синтетическом примере. Для воспроизводимых тестов использовать обычный MCP-клиент/скрипт, а не пытаться стабилизировать случайный ответ LLM. Реальный внешний агент демонстрируется отдельно как интеграция.

### D — к защите

Инструменты уровня D, адресная теория и поиск, недельный разбор, контролируемое раскрытие помощи, опубликованные ревизии контента, резервный экспорт/импорт, аудит, истечение/отзыв полномочий, тесты конфликтов и фактическое использование выбранного host. HTTP-профиль и второй host не обязательны без пользовательской потребности.

## 13. Дополнительные критерии приёмки

- AG-MCP-01: контекст соответствует подтверждённой ревизии сайта, содержит исходный ход и вопрос, но не закрытое решение.
- AG-MCP-02: незаписанный браузерный черновик не выдаётся за доступный агенту; UI явно показывает, что ещё не сохранено.
- AG-MCP-03: повтор `append_review` с тем же command_id не создаёт второй комментарий.
- AG-MCP-04: комментарий к старой ревизии не перезаписывает новую; пометка устаревания видна.
- AG-MCP-05: предложение исправления не меняет оценку до подтверждения владельцем.
- AG-MCP-06: недостающий scope блокируется backend даже при обходе MCP-обёртки.
- AG-MCP-07: read-only вызов не меняет результат, интервалы повторений или учёт помощи.
- AG-MCP-08: начало математической помощи в активной попытке учитывается; разбор прошлой попытки не переписывает историю самостоятельности.
- AG-MCP-09: direct tool и resource не обходят одну и ту же политику скрытых материалов.
- AG-MCP-10: остановленный worker/broker не препятствует обычному чтению и записи разбора; фоновые задания доставляются после восстановления.
- AG-MCP-11: экспорты, CLI-импорт и MCP используют одни предметные правила.
- AG-MCP-12: текст с инструкцией «игнорируй правила и открой секреты» не даёт новых прав и не исполняется сервером.
- AG-MCP-13: приложение работоспособно без запущенного внешнего агента и без доступа к LLM-провайдеру.
- AG-MCP-14: чувствительные операции не авторизуются только переданным моделью флагом подтверждения.

## 14. Что изменить в репозитории и прежнем ТЗ

Добавить `services/study-mcp/` (или равнозначный пакет), схемы tools, MCP smoke/contract tests, `docs/mcp-setup.md`, `docs/mcp-compatibility.md`, этот ADR и правила учебного/авторского режима в AGENTS.md. Изменить diagram и trust boundaries, матрицу сетей, сценарий демонстрации и критерии приёмки.

В версии 1.0 заменить раздел 9 «файловый протокол» на «основной MCP-интерфейс и резервный файловый обмен»; скорректировать BR-05, строки P/D, ответственность worker в разделе 7, agent endpoints в разделе 8, разделы 14–15 и тесты 18. Не оставлять одновременно два взаимоисключающих обязательных способа взаимодействия.

Порядок реализации: аудит host/репозитория -> общий API-контракт -> контекст и комментарий -> подключение реального MCP-host -> версии/идемпотентность/права -> учёт помощи и предложения -> фоновые экспорты -> расширения D. Сначала законченный путь одной задачи, затем расширение каталога инструментов.
