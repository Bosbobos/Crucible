# 04. Производство, приёмка и подключение изображений

**Редакция 3.0.0.** Пакет не требует ждать весь арт до начала разработки. Владелец генерирует по одному изображению; агент параллельно внедряет UI/RPG и готовит реальные уже предоставленные источники.

## 1. Что создано и что ещё требуется

45 художественных целевых ID: BASE ×1, броня ×6, мечи ×6, щиты ×6, мантии ×6, реликвии ×9, шёлк/ниша ×2, залы/Конклав ×6, задние орнаменты ×3. Из них **6 источников выполнены**: база и пять броней. Ещё есть `SWORD-POSE-REF` как reference, не отдельная 46-я награда.

Осталось **39 целевых самостоятельных исходников/извлечений**, не обязательно 39 новых генераций: SWD-03 сначала попытаться получить извлечением существующего примера. Дополнительно может потребоваться **один общий технический HAND-R-GRIP-01**, только если безопасно извлечь хват не удастся. Он не входит в 45 художественных целей и не требует шести вариантов по сетам.

Старая схема «14 батчей ×3 +2 резервных» отменена. Исторический лимит 48/50 не трактуется как известный текущий остаток генератора. Новая политика — не генерировать лишнее, считать фактические выходы/ремонты в журнале; не обещать определённую квоту без данных аккаунта.

## 2. Очереди

| Очередь | Работа | Блокирует ли код/учёбу |
|---|---|---|
| P0 | Подготовка BASE и пяти броней; masks, registration, proof двух крайних силуэтов | Нет; gallery/placeholder уже доступны |
| P1 | SWD-03 из примера, общий хват, ORN-01, кандидат ARM-05 | Нет; slot data/API уже существуют |
| P2 | SWD-00/01/02/04/05 и ORN-02/03; ENV-SILK/ENV-ARCHIVE | Нет |
| P3 | SHD-00…05, CLK-00…05, REL-01…09, HALL-* | Нет |

Не нужно дождаться ARM-05, чтобы проверить имеющиеся пять сетов. Проверка новых крупных плеч ARM-05 будет отдельным gate после его принятия. Не расходовать генерации на иконки, thumbnail, маски, простую эмблему и дисциплинарные SVG.

## 3. Формат результата — сразу для целевого использования

**Слои героя** (BASE, armor plates, swords, shields, cloaks, ornaments, grip patch): 1024×1536, одинаковая система координат. Генерировать отдельные мечи/щиты сразу в нужной сценической ориентации, а не вертикальный товарный shot, который затем приходится заново ставить в руку. Иконки получаются crop из alpha bbox.

**Реликвии:** 1024×1024, один предмет, прозрачный фон. **ENV/HALL:** 1536×1024, непрозрачная светлая композиция с тихой зоной под DOM-текст. При другой поддерживаемой размерности сохранять ratio и делать документированное пропорциональное нормирование, не растягивать по одной оси.

Во всех запросах один результат, без триптиха/контакт-листа, вторых ракурсов, текста и интерфейса. Не просить генератор одновременно выдать исходник, маску, иконку и готовый композит.

Прозрачный PNG предпочтителен. Если настоящий alpha недоступен — ровный белый технический фон без тени; **это честно opaque source**, не готовый layer. Magenta больше не обязательный fallback: в частности она плохо сочетается с аметистами и цветовыми кромками. Никакой рисованной шахматной сетки.

## 4. Фактический входной аудит

`10_ASSET_REGISTER.md` и `data/source_assets.json` содержат метаданные и SHA-256 **реальных семи файлов**. BASE, ARM-03, SWORD-POSE-REF полностью непрозрачны по alpha; белый фон нужно отделить. У ARM-00/01/02/04 есть прозрачные области, однако максимум alpha 254 и медиана ненулевых пикселей 253: это не автоматический брак, но требует проверки границ/внутренней непрозрачности.

Нельзя считать RGBA = готовый PNG без фона. Нельзя глобально удалить белое: так исчезнут ткань/эмаль. Использовать сохраняемые контуры/маски объекта и осмысленную edge cleanup. Нельзя автоматически усилить весь alpha «до 255», уничтожая антиалиасинг/полупрозрачность кристаллов.

## 5. Pipeline агента

1. Сохранить immutable raw и checksum, указать provenance и uploaded filename. Не перезаписывать референс сжатой производной.
2. Проверить canvas/mode/alpha/поля и соответствие визуальному ID. Зафиксировать реальные defects; не использовать старые запреты по одному basename.
3. Получить объектную маску фона; сохранить editable SVG/grayscale исходник. Контроль на белом, графитовом и циановом фоне.
4. Измерить реальный rig BASE. Зарегистрировать plate целиком переносом, единым scale и малым rotation, записав матрицу. У каждого источника одна согласованная система, а не случайные transforms частей.
5. Вырезать `chest/shoulders/bracers/legs` по реальным границам и `hide_base` отдельно. Тело/голову/хвост из бронепластины не копировать. Пояс/сумка/короткие нижние панели — legs.
6. Проверить отдельные части, полный набор, mixed outfits и none-state. При missing pixel material требуется локальный ремонт, а не расширение маски до огромной дыры.
7. Принять конкретную репрезентацию, создать WebP/thumbnail и manifest с dimensions/hash/rig/version. Переключать production manifest атомарно.
8. Подключить изображение без миграции ownership/XP: предмет уже имеет стабильный ID, меняется только art representation.

Генерация не гарантирует пиксельное совпадение. Uniform registration допустима; необходимость неравномерно вытянуть ноги/сместить лицо — failed pose, не «автоматически подогнано». Стартовый порог uniform scale около ±3% относительно нормализованного plate — ориентир для ручного review, а не повод деформировать героя до совпадения.

## 6. Выходные каталоги (производственные артефакты агента)

```text
art/raw/<asset-id>/<source-hash>.png
art/rig/<rig-id>/base.png
art/rig/<rig-id>/regions/*.png
art/rig/<rig-id>/editable.svg
art/rig/<rig-id>/rig.approved.json
art/processed/<asset-id>/<revision>/paint/<part>.png
art/processed/<asset-id>/<revision>/hide-base/<part>.png
art/processed/<asset-id>/<revision>/editable.svg
art/processed/<asset-id>/<revision>/registration.json
art/processed/<asset-id>/<revision>/qa.json
public/art/<content-hash>/<part>.webp
public/art/<content-hash>/icon.webp
```

Эти пути — **целевые выходы**, в текущем пакете они не существуют. Не писать в manifest выдуманный URL. `references/` — реальные входы, не runtime catalog. Поля `path=null`, `status=missing/not_prepared` допустимы и обязательны до получения производной.

## 7. Состояния и QA-gate

Жизненный цикл конкретной репрезентации: `missing → reference_available → processing → qa_failed/runtime_ready`. Статус полного источника и статус каждого из четырёх слотов различаются; принятие chest не автоматически принимает legs. При изменении source/registration/mask сбросить готовность затронутых производных до нового QA.

Проверка:

- Один правильный объект, нужная ориентация и canvas; без чужого лица/кожи/фона в gear layer.
- Корректные alpha и края на трёх QC-фонах, без цветных/белых ореолов и потери белой эмали.
- При 1024×1536 контрольные anchors стремятся к отклонению ≤10px, wrist/grip ≤6px; заметный шов ≤2px — цель контроля, не гарантия генератора. Большой дефект нельзя принять из-за формального среднего значения.
- Preview в 160px карточке и 240/360/480px сцене; вся фигура, хвост, клинок и орнамент помещаются.
- Нет дублей головы/когтей, исчезновения хвоста, торчащих базовых бёдер, артефактов wrap или перекрытого лица.
- Для меча: нейтральная кисть заменена один раз, рукоять под передними пальцами, клинок перед ногами, bracer не съехал.
- Для орнамента: он позади головы, не нарисован поверх рогов, выключается отдельно.

Числовой формат файла не заменяет визуальную приёмку. `qa.json` содержит реальные screenshots/contact sheets, проверенную версию rig, defects и reviewer/status. `not_run` не считать `passed`.

## 8. Как пользователь приносит очередной результат

Владелец берёт **один** файл из `art_prompts/`, прикладывает перечисленные там реальные референсы и получает один PNG. Затем передаёт агенту файл с целевым ID либо явно указывает, к какому ID он относится. Агент записывает новый source hash, проверяет и готовит производные. Не переписывает соседние уже принятые ассеты, не меняет их IDs/условия и не требует повторной генерации всего набора.

При необходимости ремонта агент выдаёт один конкретный полный prompt с приложением ровно проблемного источника и BASE/pose reference, описав один фактический дефект. Нельзя направлять неподтверждённый generic repair на все изображения. Ремонты не создают новые игровые предметы.

## 9. Иконки, gallery и placeholder

Иконки — bbox-crop принятых слоёв с padding около 12%; для paired shoulders/bracers показать обе части в понятной композиции, не генеративно перерисовать. Gallery хранит full-plate источники с честной подписью. Пока slot QA pending, показывать источник только в gallery/detail как «Образ комплекта», не как готовый equipped composite.

Placeholder — собственный одноцветный SVG категории и текст, никогда чужой rejected финал. На теле missing предмет не получает маску скрытия. Клавиатурный список loadout остаётся доступным. Поведение при image load error задаётся в paper-doll ТЗ.
