# Действующая архитектура

Приоритет: ADR-003 → ADR-002 → исходное ТЗ. Документы `Task/` остаются источником требований и историей решений. Старые положения о едином study-api, общем каталоге и обязательном файловом inbox заменены ADR-003/002.

Content публикует проверенный файловый bundle в собственную БД как неизменяемый release с SHA-256. Обычные ответы содержат только условие, метаданные и разрешённые темы. Тексты подсказок и решений доступны practice через отдельный внутренний endpoint и отдельный scope.

Practice получает закреплённое условие перед началом транзакции. В собственной БД сохраняет попытку, её редакцию, квитанцию команды и значимые факты в outbox. Черновик не попадает в события. Начатая попытка сохраняется и завершается без content и learning.

Learning получает каталог и факты через отдельную quorum-очередь, защищается от старых редакций и повторов. Курсор отражает непрерывный префикс последовательности, а не максимум полученного номера. Расчёты выполняются только в learning: окно последних пяти независимых семейств, интервалы 1/3/4/10/25/50, критерий переноса и подбор. Redis ускоряет сводку; план и настройки хранятся в PostgreSQL.

Reports имеет jobs API и consumer в одном контейнере. Запрос экспорта создаёт job и outbox. Consumer читает разрешённые снимки владельцев и уже рассчитанную learning-сводку, затем сохраняет артефакт и manifest в reports_db. Новый прогресс отмечает старые экспорты как устаревшие. Обычный разбор не зависит от reports.

Web композирует независимые ответы и передаёт команды владельцам. В нём нет формул освоения. Лаборатории — локальные математические демонстрации, не второй планировщик. Markdown не исполняет HTML/JavaScript; KaTeX работает с `trust=false`, библиотеки и шрифты поставляются локально.

Один backend-язык — Python. Каждый образ предметного API содержит только собственный предметный пакет и технические библиотеки/контракты. Общего ORM нет. `platformkit` содержит соединение с БД, аутентификацию, транзакционную квитанцию и транспорт; предметные модели остаются в сервисах.

Один физический PostgreSQL-кластер с четырьмя БД — общий отказовый домен. Две реплики и три брокера на одном ноутбуке демонстрируют отказ процессов, а не устойчивость к потере устройства или диска.

## Подготовка и развёртывание

`scripts/deploy` — операторская обёртка над Docker CLI, без host Python. Отдельный `compose.bootstrap.yaml` создаёт или проверяет секреты перед загрузкой основного Compose. Одноразовые `migrations` и `content-init` завершаются до готовности web; content-init публикует через API content только при отсутствии активного release и при первом наполнении ждёт его проекцию в learning. Повторный старт не активирует изменённые авторские файлы автоматически. Операция `scripts/deploy publish` остаётся явной.

После старта/пересоздания namespaces операторская процедура применяет и проверяет firewall. Восемь постоянных контейнеров daily сохраняются; bootstrap, migrations, content-init, tools и probe — одноразовые. Успешный запуск требует проверенных правил и доступных предметных чтений. Runtime-readiness API по-прежнему зависит только от собственной БД; отказ broker/cache после запуска не запрещает локальные записи practice.

## Контейнерные инструменты владельца

compose.tasks.yaml разделяет unit-tests (без сети), integration-tests (API-сеть) и operator (Docker CLI + socket, явный административный запуск). Последний монтирует checkout по тому же абсолютному пути, чтобы вложенные Compose/bind mounts ссылались на host-пути. Это клиент прежнего Docker Engine, не второй daemon. MCP — отдельный узкий образ/профиль без Docker socket; пока host держит stdio-сессию, он добавляет один временный контейнер к восьми основным daily. E2E выполняет Playwright в namespace web с локальным proxy для сохранения browser Origin. Локальные Python/Node остаются лишь необязательными developer-инструментами.
